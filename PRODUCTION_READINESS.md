# Production Readiness Roadmap — Reputation Management Platform

_Generated 2026-06-14 from an 8-dimension audit of the actual codebase (engine + API + console). 90 findings: **32 P0** (must-fix before national launch), **37 P1** (scale & quality), **21 P2** (differentiation). Point-in-time; verify against current code before acting._

## Executive summary

This is an unusually well-engineered core engine wrapped in a product that is NOT yet sellable: roughly 60-70% of the way to a nationally-sellable v1, with the remaining gap concentrated in commercialization, multi-tenancy, and operations rather than core logic. I verified the most consequential P0s directly in source and they are real and accurate: build_gap_model (ai_state_audit.py:942-946) unconditionally persists the synthesis result, so a transient LLM failure silently writes an EMPTY gap model that poisons the entire downstream strategy/content/report chain, and it reads the latest run with no finished_at/status filter (line 898-901, unlike diff() at 958) so it will synthesize off budget-aborted partial runs; the session cookie is set without Secure/__Host-/SameSite=Strict (auth_router.py:30); cost._unrecorded_writes is a process-global that never resets (cost.py:50,88,122) so one DB blip fails-closed every tenant indefinitely; and the engine measures model-memory not the live web for 3 of 4 engines (Anthropic/Gemini have no grounding tool, Gemini still points at the retired gemini-1.5-pro) — which undermines the headline metrics the whole product sells. The single biggest theme is that the product has NO path to revenue and NO account model: there is no organizations/accounts entity, no billing, no usage metering/quota enforcement tied to plans, and no self-serve onboarding, so it literally cannot be sold or charged for, and LLM cost-to-serve (the dominant COGS) is unbounded per customer. The second theme is operational blindness: no error tracking, no metrics/alerting, shallow health checks, a single fragile FIFO worker with no retries/reaper/leases (one crash permanently blocks a tenant's audits), no backups/DR, no hosted prod deployment, and no legal/compliance layer (ToS/AUP/privacy/DPA, CCPA, FTC 2024 fake-review rule). The third theme is output-quality credibility: multi-engine coverage is effectively absent (only Anthropic configured), the 44-case golden set is too thin and single-labeler to defend national accuracy claims, metrics are reported as point estimates with no confidence/sample size, and timeline/competitor/persona features rest on invented constants or crude heuristics that an informed buyer can debunk. The good news: the data-integrity invariants, prompt-injection fencing, SSRF netguard, human-gating, cost-tiering, batch.py (a ready 50% discount), and the agentic interrupt/resume layer are genuinely strong foundations — the work ahead is mostly building the commercial/operational shell and closing a handful of correctness leaks, not rebuilding the engine.

## Top risks if launched as-is

- Selling a deliverable whose headline numbers are wrong: 3 of 4 engines measure model-memory not the live web, only Anthropic is actually configured, and accuracy is validated on a 44-case single-labeler golden set — a prospect who checks ChatGPT themselves immediately distrusts the product, and a transient LLM failure can silently ship an empty/hollow strategy (build_gap_model bug).
- Legal/regulatory exposure with zero mitigations: no ToS/AUP/Privacy/DPA, no CCPA/CPRA handling for scraped third-party PII forwarded to LLM subprocessors, no FTC 2024 fake-review/Endorsement-Guides controls on a first-class review-generation feature, and unlicensed Reddit scraping — any one is a material liability or enforcement/press risk at national scale.
- Uncontrolled gross margin: LLM spend is the dominant COGS and there is no plan/quota/entitlement enforcement — the only guard is a per-business $50 cap that aborts work mid-run; a single trial or compromised editor account can drain the shared API key, and there is no platform-wide spend ceiling.
- Operating blind and fragile: no error tracking, metrics, alerting, backups/DR, or real health checks, plus a single FIFO worker where one crash leaves a 'running' row that permanently blocks a tenant's audits — failures are discovered by customer complaints, and a DB loss is unrecoverable.
- No way to charge or onboard at scale: no accounts/billing/signup means every customer, password reset, and budget change is a manual ops ticket and there is literally no path to revenue — the product cannot be sold even if the engine were perfect.
- Account-takeover/security surface: non-Secure session cookie over plaintext, no password policy, stateless 12h JWTs with no revocation, in-process rate limiting defeated across replicas, and shared single LLM key with no per-tenant isolation — unacceptable for multi-tenant data including regulated financial clients.

## Cost-efficiency plan

Cost-to-serve is dominated by LLM spend, and the engine already contains most of the levers — they are just unwired. Stacking the four biggest, complementary levers should cut per-audit COGS by roughly 60-75% with low risk: (1) route the highest-volume call class (per-answer scoring) through the existing, tested batch.py score_run_batched for a flat 50% Batch-API discount; (2) add Anthropic prompt caching (cache_control on the fixed SCORING/GAP/content system blocks, which are re-sent 100-300x per audit) for ~90% off repeated system-prompt input tokens — order calls so the cached prefix stays warm; (3) content-hash + pgvector near-dup dedup so identical/near-identical answers across samples and adjacent runs are not re-scored (embeddings are ~100x cheaper than a scoring call); (4) bound and pre-aggregate the full-Opus gap synthesis (worst-N weak queries, map-reduce, Sonnet on basic tiers) instead of feeding the entire fenced answer set on the priciest model. Secondary levers: adaptive sampling on the engine-call dimension (gate the 2nd sample for near-deterministic grounded engines), a short-TTL answer cache, and making audit() internally resumable so flaky-provider retries don't re-spend the battery. On the connection side, thread the audit's open DB connection into cost.record/month_spend, move the budget check out of the inner sample loop, and pool engine connections (or PgBouncer) — this removes hundreds of TCP/TLS setups per audit and prevents max_connections outages that themselves cause expensive failed/retried work. On the price-vs-cost axis: build a COGS model parameterized by battery size x engines x samples using cost.py PRICING, then back-solve plan tiers (Starter/Growth/Pro/Agency) so even the cheapest plan clears target gross margin at full utilization, with engines/samples capped per tier via the existing business_config.disabled_tools/samples_per_prompt knobs and metered overage above included usage. Keep over_budget() as the fail-closed backstop beneath plan quotas, replace the flat $50 with a tier-derived budget so normal audits never truncate, and add per-account margin analytics (subscription revenue minus summed cost_ledger COGS) plus a monthly reconciliation against real provider invoices so pricing stays grounded as token rates and engine mix change. Net: deliver best-in-class output quality (real multi-engine grounding) while the batch+cache+dedup stack keeps the marginal audit cheap enough to price profitably nationally.

### Engineering quality, correctness & reliability (12)

#### [P0 · S] build_gap_model overwrites the stored gap model with {} when the synthesis LLM fails
**Problem.** In reputation_engine/rep_engine/ai_state_audit.py:942-947, build_gap_model() calls orchestrator_json(GAP_SYSTEM, payload) and unconditionally INSERTs the result. orchestrator_json returns {} on ANY LLM failure (retries exhausted, empty completion, unparseable JSON, missing key -- see _anthropic_complete/_parse_json_lenient which all return {}). So a transient provider 429/timeout, or the orchestrator key not being set, silently persists an EMPTY gap model as the latest one. Every downstream consumer then reads that empty model: strategy_generator builds a plan from nothing, run_full/run_cycle's 'plan' step produces an empty plan, content_generator has no work orders, and the client report shows a hollow strategy. This is the exact 'a failed call must not pollute outputs' invariant that the answer-scoring path was carefully hardened for (failed rows get NULL metrics + failed=True and are excluded everywhere), but the gap-model path has no equivalent guard. The team already hit a closely related incident (the Opus-4.8 prefill 400 that made every full-tier JSON call return {} -- per MEMORY), yet the empty-result is still committed.

**Fix.** In build_gap_model, treat model == {} (or missing required keys like weak_queries/summary) as a synthesis FAILURE: do NOT INSERT it, log a warning, and either raise so the runstate step is marked failed/resumable, or keep the prior good gap_models row. Mirror the score_answer pattern. Add an integration test: when orchestrator_json returns {}, assert no new gap_models row is written and the previous model is preserved.

#### [P0 · S] build_gap_model consumes the latest run regardless of status -- including budget-aborted partial runs
**Problem.** ai_state_audit.py:898-901 selects the run to synthesize with `SELECT id FROM audit_runs WHERE business_id=%s ORDER BY id DESC LIMIT 1` -- with NO `finished_at IS NOT NULL` / `status='complete'` filter. The codebase's own invariant (documented at lines 252-256 and enforced in diff() at line 959, tracking, reports, learning) is that aborted/in-progress runs keep finished_at NULL and must be excluded from every downstream metric because they are non-representative. build_gap_model violates that invariant: if an audit hits the mid-run budget cap (audit() returns early with status='aborted', finished_at NULL) and a cycle then runs gap_model, the strategy is built off a partial, biased sample of the prompt battery. Same hazard if gap_model is invoked while an audit is still in_progress.

**Fix.** Filter the run selection to `WHERE business_id=%s AND finished_at IS NOT NULL AND status='complete' ORDER BY id DESC LIMIT 1`, matching diff(). If no completed run exists, raise the existing 'Run an audit first' error rather than synthesizing off a partial run. Add a test that an aborted run is skipped by build_gap_model.

#### [P1 · M] No reaper for stuck jobs / dangling audit runs -- a single crash permanently blocks a tenant's job type
**Problem.** api_jobs (alembic 0008) has no lease/heartbeat/attempts column. jobs.run_job (api/jobs.py:100) flips status to 'running' then executes in-process; if the web process (inline BackgroundTasks, the DEFAULT JOB_WORKER=inline per settings.py:40) or the worker (worker.py) dies mid-job, the row stays 'running' forever. jobs.enqueue (jobs.py:84-90) refuses to enqueue when a same-type job is in ('queued','running'), so the stuck row makes EVERY future audit/cycle for that business return 409 permanently -- a paying tenant's audits silently stop until someone manually UPDATEs the DB. The same applies to audit_runs: only the budget-abort path sets status='aborted' (ai_state_audit.py:807); any exception/crash inside audit() leaves audit_runs in_progress with finished_at NULL forever (and, because of the session advisory lock, no immediate re-run hazard, but the run is orphaned). There is no `now() - started_at > interval` reaper anywhere in the codebase (confirmed by grep).

**Fix.** Add a reaper: a periodic query that marks api_jobs rows 'running' longer than a max-runtime threshold as 'failed' (error='timed out / process died') and audit_runs in_progress past a threshold as 'aborted'. Run it on worker startup and on an interval. Add an attempts/lease_expires_at column so the claim can be re-acquired safely. Cover with a test that a stale 'running' job no longer blocks enqueue.

#### [P1 · S] cost._unrecorded_writes is process-global and never reset -- one DB blip fails-closed ALL tenants for the process lifetime
**Problem.** cost.py:50 declares a module-global `_unrecorded_writes`; record() increments it on any cost-write failure (line 88) and over_budget() returns True whenever it is > 0 (lines 122-124). This is per-PROCESS, not per-business, and is never decremented/reset. In a long-running multi-tenant API/worker, a single transient cost_ledger insert failure (deadlock, brief connection drop) makes over_budget() return True for EVERY business indefinitely -- audit() then raises SystemExit 'over budget' for all tenants (ai_state_audit.py:737-742, 802) and every agent_tools llm_* call raises BudgetExceededError -- until the process is restarted. Fail-closed is the right policy, but the blast radius and permanence are wrong: it conflates 'this one tenant's spend is unverifiable right now' with 'the whole engine is poisoned forever'.

**Fix.** Scope the unrecorded-write tracking per business_id (a dict) and/or make over_budget re-verify against the ledger and clear the flag once a subsequent write for that business succeeds. At minimum, decrement/reset on the next successful record() so a transient blip self-heals. Add a unit test that a failed-then-succeeded cost write does not permanently brick over_budget for other businesses.

#### [P1 · M] Schema defined twice: alembic (source of truth) AND ~12 modules' inline CREATE/ALTER DDL that runs in request paths
**Problem.** Despite alembic 0001-0010 being declared the schema source of truth, ai_state_audit.SCHEMA + init_db's ALTER TABLE ADD COLUMN IF NOT EXISTS (lines 188-257), content_generator._ensure_table, citation_analytics._ensure, competitor._ensure, mention_monitor._ensure, external_signals._ensure_table, production_brief._ensure_table, runstate._ensure_tables, and the four agent_* modules each carry their own CREATE TABLE IF NOT EXISTS / ALTER DDL executed at call time. Two definitions of the same table WILL drift (column type, default, index, FK ON DELETE, NOT NULL) and the inline `IF NOT EXISTS` silently no-ops against the alembic-built table, hiding the divergence -- until a query assumes a column/constraint that only one definition has. It also means tenant-facing engine calls run DDL (ALTER TABLE) on every invocation (e.g. audit() -> init_db()), which is unnecessary work and can contend with migrations. This is a correctness-of-schema and maintainability hazard for a product that must run 'with no bugs'.

**Fix.** Make alembic the ONLY DDL. Delete the inline CREATE/ALTER from the engine modules (or guard them behind a dev-only flag), and add a CI check that fails if a table referenced in code is missing from migrations. At minimum, add a test that diffs the alembic-built schema against the inline DDL to assert they agree. Stop running init_db()/_ensure() inside hot per-request engine calls.

#### [P1 · M] Engine LLM keys / orchestrator config are read once at import time, diverging from validated config and blocking per-tenant keys
**Problem.** ai_state_audit.py:69-99 reads ORCHESTRATOR, ANTHROPIC_API_KEY, OPENAI_API_KEY, PERPLEXITY_API_KEY, GEMINI_API_KEY and the model ids as module-level globals at IMPORT time, and active_engines()/the adapters branch on the 'YOUR_*' placeholder substring of those frozen globals. Meanwhile config.py validates the same env via load_settings() (a separate, cached source). Consequences: (1) two sources of truth that can disagree -- preflight/config can say a key is set while the audit module froze the placeholder, or vice versa, depending on import order; (2) keys cannot be rotated or set after import without re-importing the process; (3) there is no path to per-business/per-tenant keys (the product targets national multi-tenant sale, where customers may BYO keys or you isolate spend per tenant). For a national multi-tenant SaaS, global import-time single-key config is a real limitation.

**Fix.** Route all engine key/model/orchestrator lookups through config.load_settings() (or a small accessor) read at CALL time, so config has one source of truth and keys can change without reimport. Plan a per-business credentials path (a key resolver keyed by business_id) so tenants can be isolated; thread business_id into the adapters/orchestrator calls. Add a test that setting a key via env after import is picked up.

#### [P1 · S] content_generator.approve() is not idempotent -- re-approving a draft creates duplicate assets
**Problem.** approve() (content_generator.py:410-436) SELECTs the draft and unconditionally INSERTs a new row into assets, then sets the draft to 'approved'. There is no guard against the draft already being 'approved'/'rejected'. Calling approve twice (double-click in the console, a retried API request, two reviewers) inserts TWO assets for one draft and double-advances the work order. The API content router likely calls this; combined with no row lock, concurrent approves race. For a human-gated publishing workflow where the asset list is the system of record, duplicate published assets are a data-integrity bug that surfaces in client reports and citation tracking.

**Fix.** Make approve() idempotent: only proceed when status='pending_review'/'needs_fix' (e.g. `UPDATE content_drafts SET status='approved',... WHERE id=%s AND status IN ('pending_review','needs_fix') RETURNING id` and only INSERT the asset if a row was updated), or check published_asset_id IS NULL first, inside one transaction with SELECT ... FOR UPDATE. Add a test that double-approve yields exactly one asset.

#### [P1 · S] audit() crash mid-run leaves audit_runs orphaned 'in_progress' and the answers partially written without abort marking
**Problem.** In audit() (ai_state_audit.py:770-869), only the explicit budget-cap branch sets status='aborted' and commits (lines 804-809). If any engine adapter, score_answer, or DB call raises an unhandled exception partway through the battery, the function propagates the exception with the audit_runs row still status='in_progress', finished_at NULL, and a partial set of answers rows already committed via the per-row inserts. Unlike a budget-abort, this orphaned run is never marked aborted, so it lingers as in_progress (excluded from finished_at-gated metrics, which is good, but never cleaned up and indistinguishable from a genuinely running audit by the reaper-less system). Over time these accumulate; runs_status and the jobs UI show perpetual in_progress rows.

**Fix.** Wrap the battery loop in try/except that, on any exception, marks the run status='failed' (or 'aborted') with finished_at left NULL and re-raises -- so the runstate step is recorded failed and the run is resumable/identifiable. Pair with the reaper finding so orphaned in_progress runs age out. Add a test that an engine raising mid-audit leaves the run marked failed, not in_progress.

#### [P2 · M] audit step is not internally resumable -- a resumed cycle re-runs the entire (expensive) prompt battery
**Problem.** runstate gives step-level resumability: run_cycle/run_full skip whole steps whose step_key is 'done' (runstate.py:97-99). But audit() is a single opaque step that is NOT internally checkpointed -- if a cycle fails during 'audit' (e.g. provider outage at prompt 30 of 40), resuming re-enters the 'audit' step from scratch and re-spends the full battery x engines x samples, re-querying every prompt already answered. The module docstring for runstate explicitly promises 'resume without re-spending API budget on steps that already completed', but the single most expensive step doesn't honor that within itself. The answers table already has run_id+prompt+engine+sample_idx, so completed (prompt,engine,sample) tuples are identifiable.

**Fix.** Make audit() resume-aware: when resuming an existing in_progress run for the business, skip (prompt,engine,sample) tuples already present in answers for that run_id, rather than starting a new audit_run. This turns the costliest step into a true resumable operation and protects budget on flaky provider days. Cover with a test that re-invoking audit after a partial run only fills missing tuples.

#### [P2 · M] CI gates only F/E9 lint; mypy, full ruff, and bandit are advisory (|| true), and coverage floor is 50%
**Problem.** .github/workflows/ci.yml runs only `ruff check --select F,E9` as blocking (line 53); the full ruleset (line 56), bandit SAST (line 59), and mypy type-check (line 62) all end in `|| true`, so type errors, security findings, and style/bug-prone patterns CANNOT fail the build. Coverage floor is --cov-fail-under=50 (line 67) against a measured 57.5% baseline. For a product that must ship 'with no bugs' and be sold nationally to (often regulated, financial) businesses, type-unsafety and SAST findings landing silently is a real reliability/quality risk -- mypy in particular would catch many of the None-handling and shape bugs this engine is exposed to (it threads a lot of dict-shaped LLM output around).

**Fix.** Triage the current mypy/bandit/full-ruff output, then ratchet each to blocking (drop the || true) as the team already notes is the plan. Raise the coverage floor toward ~70% and specifically cover the untested hot paths: jobs.run_job failure recording, build_gap_model failure handling, the new reaper, cost.over_budget fail-closed reset. The agentic interrupt/resume and data-integrity invariants are already well covered -- extend that rigor to the job/runner and gap-model layers.

#### [P2 · M] Engine uses a fresh psycopg connection per db() call with no pool -- concurrent jobs/audits can exhaust Postgres connections
**Problem.** db.py:39-42 opens a brand-new connection on every db() call and the engine calls db() many times per operation (each runstate.step does 3 separate db() open/commit/close cycles; audit/gap/citation/etc. open dozens). The API request path has pool.py (max 8) and the langgraph PostgresSaver has its own pool (max 4), but ENGINE code -- which is what the background worker and inline BackgroundTasks actually execute -- bypasses both and opens raw connections. Under concurrency (N worker processes/threads each running a cycle that fans out to ~10 modules, plus the API pool, plus the saver pool), total connections can exceed Postgres max_connections (default 100), causing 'too many clients' failures that surface as job failures. pool.py's own comment acknowledges the combined-connection risk but the engine path isn't pooled.

**Fix.** Introduce an optional pooled connection source in db.py (a process-wide ConnectionPool slotted behind the existing `with db() as conn:` contract, as db.py's docstring anticipates) and use it in the worker/engine path, with a documented max_connections budget across the API pool + saver pool + engine pool. Add a smoke test that runs several concurrent cycles without exhausting connections.

#### [P2 · M] http.py deadline does not bound time spent inside requests' redirect/connect, and SSRF guard has a residual TOCTOU on the initial fetch
**Problem.** Two smaller reliability items in the network layer. (1) http.request_json's `deadline` bounds the per-attempt socket timeout and skips further retries, but when guard_redirects=False (the default for LLM calls), requests follows redirects internally and the total wall-clock can still exceed the deadline because the deadline is only re-checked between attempts, not within a single requests.request that itself does multiple hops/slow connect. For LLM calls this is minor, but the 'total wall-clock budget' guarantee in the docstring is slightly overstated. (2) netguard.assert_url_allowed resolves DNS and checks IPs, then requests.request resolves again independently -- a classic TOCTOU where a rebinding host could pass the guard and connect to a different (internal) IP on the real fetch. guard_redirects re-validates each HOP, but the FIRST fetch's connect target is not pinned to the validated IP.

**Fix.** (1) Document the deadline as best-effort, or set requests' connect/read timeouts from the remaining budget AND disable internal redirect-following so every hop is deadline- and SSRF-checked. (2) For defense in depth, pin the connection to the validated IP (resolve once, connect by IP with Host header / a custom adapter) so the fetch can't hit a rebind. Lower priority since netguard already fails closed on resolution and re-checks redirect hops.

### Performance, cost & scalability (11)

#### [P0 · M] Batch API exists but is never wired into the audit cycle — scoring runs synchronously at full price
**Problem.** batch.py implements score_run_batched() over the Anthropic Message Batches API (a flat 50% discount on all token usage) but it is ONLY reachable via its own CLI (`python -m rep_engine.batch score`). The orchestrator's run_full/run_cycle call m1.audit(bid), and audit() scores every answer synchronously inline (ai_state_audit.py:824 score_answer → orchestrator_json tier='cheap'). Scoring is the single highest-volume LLM operation in the system (one call per answer per sample per engine), and it is embarrassingly parallel + latency-tolerant — the exact profile the repo's own batch.py docstring says is 'an ideal Batch API candidate'. The 50% discount on the dominant call class is being left entirely on the table in the actual product path. The synchronous path also serializes the whole audit (POLITE_DELAY_S=0.4 sleep per row + blocking HTTP), making a 4-engine audit take many minutes of wall-clock.

**Fix.** Decouple scoring from answer collection: in audit(), persist raw answers first (unscored), then score the run in ONE Anthropic batch via the existing score_run_batched(). Add a JOB_DISPATCH entry ('score_run') and call it as the next pipeline step after 'audit' in run_cycle/run_full, or have audit() submit the batch and a worker poll for completion. Keep the synchronous path as a fallback for tiny/interactive audits. This is a ~50% cut on the highest-volume call class with code that already exists and is unit-tested.

#### [P0 · M] No Anthropic prompt caching despite large, fixed system prompts re-sent on every call
**Problem.** No LLM call sets cache_control / prompt caching anywhere (grep for cache_control/ephemeral/prompt_cach returns zero hits in rep_engine). Yet every scoring call re-sends SCORING_SYSTEM (a ~1.5KB fixed system prompt, ai_state_audit.py:638-667) plus the ~250-char UNTRUSTED_INSTRUCTION, and every gap call re-sends GAP_SYSTEM. With multi-sampling × multi-engine, the IDENTICAL system block is re-sent 100-300 times per audit. Anthropic prompt caching gives ~90% off cached input tokens with a 5-minute TTL — a per-audit burst of same-prefix calls is the textbook cache hit pattern. The content generator is worse: GEN_SYSTEM/EVAL_SYSTEM/REVISE_SYSTEM/COMPLIANCE_SYSTEM are all fixed and re-sent for every work order × revision. The code comment at _anthropic_complete even notes the prompts are now larger after hardening, but caching was never added.

**Fix.** Add a cache_control:{type:'ephemeral'} breakpoint on the system block in _anthropic_complete, score_answer's batch request builder, orchestrator_text, and the content-generator system prompts (and set the anthropic-beta header where required by the chosen model). Order calls so the cached prefix stays warm within the 5-min TTL (batch scoring naturally bursts). Net effect: ~90% off the repeated system-prompt input tokens — the single cheapest high-leverage change, and complementary to the batch discount.

#### [P0 · L] Per-business cost-to-serve is unquantified and likely exceeds a viable price at full multi-engine scale
**Problem.** The product targets querying ChatGPT + Perplexity + Gemini + Claude. With the current battery (build_prompt_battery + lensed ≈ 16-18 prompt-lenses), 4 engines, and samples_per_prompt default 2, a single audit fires ~144 answer calls + ~144 scoring calls ≈ 288 LLM calls, before the gap-model synthesis (full Opus tier) and any content generation. The monthly budget default is just $50 (cost.py:115, baseline.sql:92) and over_budget() ABORTS the audit mid-run when hit (ai_state_audit.py:802-809) — so at real multi-engine scale a default-config customer's audit will truncate, producing a non-representative partial run. There is no analysis tying COGS-per-audit to a sellable monthly price, no per-tier (basic/pro) battery sizing, and the answer-engine retrieval calls (Perplexity/OpenAI-search/Gemini-grounded) are themselves expensive and uncached.

**Fix.** (1) Produce a COGS model: cost-per-audit = Σ(engine answer calls × rate) + Σ(scoring calls × Haiku rate) + gap synthesis, parameterized by battery size/samples/engines, and back-solve the battery for a target gross margin at each price tier. (2) Raise default monthly_budget_usd and make it tier-derived, not a flat $50, so a normal audit cannot truncate. (3) Add a config to cap engines/samples per plan tier so basic customers run a 1-2 engine audit and pro customers run all 4.

#### [P1 · M] Cost ledger opens a fresh DB connection on every record() and every per-sample budget check — connection churn + repeated full SUM scan inside the audit hot loop
**Problem.** audit() holds one connection for the loop, but inside the loop it calls cost.over_budget() at the TOP of every sample iteration (ai_state_audit.py:802) and cost.record() twice per scored answer (lines 820, 830). Each of cost.record(), month_spend(), and budget_for() opens its OWN fresh psycopg.connect via db() (cost.py:76,97,110) — there is no pooling in engine code (db.py:39 connects fresh per call by design). For a ~288-call audit that is hundreds of TCP+TLS+auth connection setups, and over_budget() re-runs `SELECT SUM(est_cost_usd) ... WHERE business_id=%s AND created_at >= month` on every sample — a growing cost_ledger scan. Under concurrent audits (multiple businesses via the worker) this multiplies and competes for Postgres max_connections alongside the API pool (max 8), the langgraph PostgresSaver pool (max 4), and each engine db().

**Fix.** (1) Thread the audit's open connection into cost.record()/month_spend() (accept an optional conn) so the hot loop reuses one connection instead of opening 3 per answer. (2) Move the budget check out of the innermost sample loop to per-prompt-engine granularity (checking every sample is overkill — spend doesn't move that fast). (3) Maintain a running in-memory spend tally during the audit and only re-query the ledger periodically. (4) Ensure a composite index on cost_ledger(business_id, created_at) exists so month_spend is an index range scan, not a seq scan.

#### [P1 · L] Engine-level connection pooling is absent — three independent pools plus per-call db() will collide on Postgres max_connections under multi-tenant concurrency
**Problem.** There are three disjoint connection strategies that all hit the same Postgres: (a) the API request pool (api/pool.py, max_size=8), (b) the langgraph PostgresSaver pool (agent_tools.py:174, max_size=4), and (c) the engine itself which opens a brand-new connection on EVERY db() call with no pool (db.py:39). The worker runs engine jobs that use (c) heavily (audit alone opens hundreds). The pool comments explicitly acknowledge the risk ('combined must stay under Postgres max_connections') but rely on hand-tuned small max_sizes rather than a shared/bounded pool. With multiple workers or multiple concurrent audits this is unbounded connection creation from the engine side — exactly the path that exhausts Postgres connections at scale, and there is no PgBouncer/pooler in docker-compose.

**Fix.** Introduce an optional shared engine-side pool behind db() (psycopg_pool, opt-in via env so CLI/tests keep fresh-connect behavior), OR put PgBouncer (transaction pooling) in front of Postgres in docker-compose and point all three consumers at it. Set explicit, documented connection budgets per process and assert their sum < max_connections at startup. This is required before running more than one worker or auditing many tenants concurrently.

#### [P1 · L] Single-process FIFO worker with no concurrency, priority, or fairness — does not scale to a national multi-tenant load
**Problem.** worker.py is a single while-loop that pulls ONE job at a time (`SELECT id FROM api_jobs WHERE status='queued' ORDER BY id LIMIT 1`), runs it to completion (run_forever), then polls again every 3s. There is no intra-process concurrency (one long audit blocks every other tenant's queued job behind it), no priority lanes (a quick citation_analyze waits behind a multi-minute audit), no per-tenant fairness (one heavy customer starves others), and no autoscaling signal. enqueue() also dedupes only by exact (business_id, job_type) active job, so the queue can still pile up across tenants with a single drain. Audits are minutes long, so a few concurrent customers triggering audits will serialize into a multi-hour backlog on one worker.

**Fix.** Move to a real queue with concurrency and priorities. Minimum viable: run N worker processes (the code claims it's safe — run_job claims atomically) and document horizontal scaling; better: adopt a job framework (Celery/RQ/arq/Dramatiq on Redis, or SKIP LOCKED-based Postgres queue with priority + per-tenant round-robin). Add priority and weight columns to api_jobs and order claims by (priority, fairness). Tie worker count to queue depth for autoscaling.

#### [P1 · M] Embeddings-based scoring dedup / skip is absent — identical/near-identical answers across samples and runs are fully re-scored
**Problem.** Multi-sampling re-queries the same (prompt, engine) up to samples_per_prompt times; retrieval-grounded engines frequently return near-identical answers across samples and across adjacent runs. Every one is sent to the scorer LLM as a fresh call (no dedup). The pgvector hook exists only as a no-op placeholder in the content generator (_already_covered returns False, content_generator.py:92-95) and is not used in scoring at all. The repo prompt explicitly calls out 'embeddings-based skip' as a lever, and it is entirely unimplemented. This wastes scoring spend on duplicate content and inflates per-audit COGS.

**Fix.** (1) Cheap content-hash dedup first: hash the normalized (answer_text + sorted sources) per (prompt, engine) within a run and across the prior run; if unchanged, copy the prior score instead of re-scoring. (2) Then an embeddings/pgvector near-dup check (cosine ≥ threshold) to skip re-scoring answers that are semantically identical to an already-scored one. (3) Wire the same pgvector check into content generation's _already_covered so equivalent assets aren't regenerated. Embedding calls are ~100x cheaper than a scoring call, so this is strongly net-positive.

#### [P1 · M] Gap-model synthesis runs full-Opus over the entire fenced answer set with no bound on payload size
**Problem.** build_gap_model (ai_state_audit.py:895-950) selects ALL answers for the latest run, fences each (answer_text + cited_sources + key_sources + missing, all potentially long), serializes the whole list plus external_signals into one JSON payload, and sends it to orchestrator_json at the DEFAULT 'full' tier (Opus 4.8 — the most expensive model, $0.005/$0.025 per 1K per cost.py). With 4 engines × ~18 prompt-lenses × 2 samples ≈ 144 fenced answers, this is a very large single input on the priciest model, and the payload grows unbounded with battery/engine/sample size. There is no truncation, summarization, or map-reduce — a large audit can produce an input that is both expensive and at risk of exceeding context limits.

**Fix.** (1) Pre-aggregate before synthesis: dedupe answers per (prompt,engine), keep the representative + the numeric scores, and feed the scorer's already-extracted key_sources/missing rather than full answer_text where possible — drastically shrinking the gap-model input. (2) Cap the answer set fed to synthesis (e.g. worst-N weak queries by goal_alignment) and map-reduce if larger. (3) Cache the GAP_SYSTEM prefix. (4) Consider Sonnet (mid tier) for synthesis on basic plans, reserving Opus for pro.

#### [P2 · M] Answer-engine retrieval calls have no caching/dedup across runs or businesses despite stable prompts
**Problem.** The answer engines (Perplexity/OpenAI-search/Gemini/Anthropic) are queried with a deterministic per-business battery (build_prompt_battery) that changes little run-over-run. These grounded calls are a real cost (Perplexity sonar, OpenAI web_search, Gemini grounding) and are fired fresh every audit, every sample, with no short-window caching even when the underlying web answer is unlikely to have changed between samples taken seconds apart. There is no cross-sample reuse: samples=2 means the same prompt is sent to the same engine twice back-to-back purely for variance estimation, doubling retrieval cost on prompts where adaptive sampling hasn't yet kicked in.

**Fix.** (1) For variance sampling, recognize that grounded engines are near-deterministic within a short window — gate the SECOND sample behind a quick similarity check on the first, or lower default samples to 1 for grounded engines and reserve multi-sampling for the non-grounded model. (2) Add a short-TTL answer cache keyed by (engine, normalized prompt) so re-runs/retries within a window reuse the retrieval. Adaptive sampling already exists (_should_stop_sampling) — extend the same 'don't spend where it won't change the picture' logic to the engine-call dimension, not just scoring.

#### [P2 · S] langgraph PostgresSaver pool uses the raw unvalidated DSN and opens its own pool at first agentic call
**Problem.** _pg_saver (agent_tools.py:165-178) builds its ConnectionPool from DB_DSN — the RAW env constant (db.py:30, default contains the USER:PASSWORD placeholder) — instead of the validated dsn() that every other consumer uses. A misconfigured DSN therefore fails late, deep inside a graph run, rather than fast at startup; and this is a second/third independent pool (max_size=4) created lazily, adding to the connection-budget problem above. Because it's a process-global singleton created on first use, its connections are held for the life of the worker even when no graph is active.

**Fix.** Use the validated dsn() in _pg_saver (consistent with pool.py and db.py), and fold its connection budget into the documented per-process connection accounting. If a shared engine pool or PgBouncer is adopted, route the checkpointer through it too rather than spinning a third independent pool.

#### [P2 · L] No usage metering / quota enforcement ties LLM spend to billing — cost is tracked but not monetized or capped per plan
**Problem.** cost_ledger records estimated spend and over_budget() enforces a single per-business monthly cap, but there is no usage-metering layer that maps recorded spend to a subscription plan, enforces per-plan quotas (audits/month, engines, samples, content drafts), or surfaces cost-to-serve vs. price. The known-state note confirms NO billing/subscriptions and NO usage metering/quotas. Without this, the dominant variable cost (LLM spend) is unbounded per customer relative to what they pay — a default $50 cap is the only guard, and it aborts work rather than gating features. This is a direct margin risk at national scale.

**Fix.** Add a plan/entitlements layer: per-plan quotas for audits, engines, samples, gap syntheses, and content drafts, enforced before enqueueing jobs (not by mid-run abort). Roll cost_ledger up into a per-business monthly usage view and reconcile against plan price for margin visibility. Make the budget cap a soft alert + feature gate, with mid-run abort reserved as a final backstop.

### Security & data protection (10)

#### [P0 · S] Session cookie is set without the Secure flag (and not SameSite=Strict / __Host- prefix)
**Problem.** In reputation_engine/rep_engine/api/routers/auth_router.py the login handler sets the auth cookie as response.set_cookie("rc_token", token, httponly=True, samesite="lax", path="/", max_age=max_age) with NO secure=True. The httpOnly session JWT is therefore transmitted over any plaintext HTTP request and can be sniffed on the wire, defeating the whole cookie-hardening effort. The CSRF cookie has the same problem. samesite="lax" (not strict) also still allows the session cookie to ride along on top-level cross-site GET navigations, and there is no __Host- prefix so a subdomain/path could shadow the cookie. Selling nationally means TLS-terminated multi-tenant traffic where a non-Secure session cookie is an account-takeover vector.

**Fix.** Set secure=True on both rc_token and csrf_token (driven by an env flag like COOKIE_SECURE defaulting to True in prod, False only for local http dev). Prefer samesite="strict" for rc_token (the SPA is same-origin to the API via CORS+credentials; if cross-site is required keep lax but pair with the existing CSRF check). Rename to __Host-rc_token (requires Secure, path=/, no Domain) to lock the cookie to the exact origin. Add an explicit test asserting Secure is present in the Set-Cookie header in prod mode.

#### [P1 · M] No password strength policy or email validation on user creation/login
**Problem.** reputation_engine/rep_engine/api/schemas.py declares LoginRequest and CreateUserRequest with email: str and password: str — no pydantic EmailStr, no minimum length, no complexity/blocklist. admin.create_user() (routers/admin.py) hashes whatever it receives, and seed_admin() (auth.py) accepts any ADMIN_SEED_PASSWORD including trivial ones (docker-compose default guidance is 'change-me'). For a SaaS holding multiple businesses' reputation/competitive data, admin-set 1-char passwords are a credible account-takeover path, and unvalidated emails let malformed/duplicate-by-confusable accounts in.

**Fix.** Use EmailStr for email fields (add email-validator) and a constrained password type (min length ~12, reject common/breached passwords via a small denylist or zxcvbn-style check). Enforce the same policy in seed_admin and reject obviously-weak seed passwords with a startup warning/error. Add a self-service password-change endpoint while you are here (none exists today).

#### [P1 · L] No JWT revocation, refresh, or secret rotation — logout only clears the cookie
**Problem.** auth.create_token() issues a 12h (JWT_TTL_MIN default 720) HS256 token with only sub/email/role/iat/exp and no jti. /auth/logout (auth_router.py) merely response.delete_cookie(...) — the token stays valid until exp, so a captured token (or a token held by a now-disabled/role-changed user) cannot be invalidated server-side; only is_active is re-checked per request (deps.get_current_user), and the role is read from the token, not the DB, so an admin-to-client demotion does not take effect until expiry. There is a single JWT_SECRET (settings.py) with no key id (kid) or rotation path, so rotating the secret instantly logs everyone out and any leaked secret forges tokens for all tenants. No refresh-token flow means a short TTL forces frequent re-login (pushing operators toward long, riskier TTLs).

**Fix.** Add a jti to tokens plus a server-side revocation list (a small revoked_tokens / sessions table keyed by jti+exp, or bump a per-user token_version column checked on each request) so logout, password change, and deactivation revoke immediately. Read role (and access) from the DB per request rather than trusting the token claim. Support a short access token + rotating refresh token, and add JWT_SECRET rotation via a kid header with a current+previous key set so rotation does not mass-logout.

#### [P1 · M] Rate limiting is in-process only and absent on expensive job-trigger endpoints
**Problem.** ratelimit.py is a module-level in-memory dict (_ATTEMPTS) — in a multi-process/multi-replica deployment (docker-compose already runs api + worker; prod will run N uvicorn workers) the login brute-force limit is per-process, so an attacker spreads attempts across workers and the limit barely bites. Worse, the ONLY rate-limited route is /auth/login; the expensive endpoints have none. POST /businesses/{id}/jobs/{job_type} (jobs_router.py) lets any editor enqueue audit/cycle/normalize_signals jobs that fan out to many paid LLM + crawl calls; the only guard is a per-(business,job_type) 409 dedupe and the per-business monthly budget cap. An authenticated editor (or a compromised editor account) can rotate job_type and burn the full monthly budget of every business they can edit, and there is no global spend cap across tenants.

**Fix.** Move rate-limit state to a shared store (Redis or a Postgres token-bucket table) keyed by IP and by user. Add per-user / per-business throttles on job triggers and on /external-signals ingestion (which feeds paid normalization). Add a platform-wide daily/monthly spend ceiling in addition to the per-business cap so a multi-account abuse pattern can't drain the API key. Consider a minimum interval between same-business audits.

#### [P1 · M] Dependencies are unpinned with no lockfile and no automated vulnerability scanning
**Problem.** reputation_engine/requirements.txt uses floor constraints only (requests>=2.31, fastapi>=0.110, pyjwt>=2.8, langgraph>=1.0,<2, etc.) with no hash-pinned lockfile, and the Next.js console pulls a large node_modules tree. CI (.github/workflows/ci.yml) runs bandit -ll and mypy as advisory (|| true) and gitleaks with continue-on-error: true — i.e. NOTHING in the supply-chain/SAST chain can fail a build. A transitive dependency CVE (e.g. in requests/urllib3, pyjwt, or a langchain dep) ships silently, and there is no pip-audit / npm audit / Dependabot. For a product holding customer business data this is a real supply-chain exposure.

**Fix.** Pin exact versions with a lockfile (pip-tools/uv compile with hashes for Python; commit package-lock.json for the console) and rebuild from the lock. Add pip-audit and npm audit (and ideally Trivy/osv-scanner) as BLOCKING CI steps, and enable Dependabot/Renovate. Set a date to flip bandit (high/medium) and gitleaks from advisory to blocking after one triage pass.

#### [P1 · M] netguard validates the host but the real fetch re-resolves DNS (TOCTOU / DNS-rebinding window)
**Problem.** netguard.assert_url_allowed() (netguard.py) resolves the hostname via socket.getaddrinfo and checks the IPs, but then http.request_json()/site_crawl/firecrawl issue the request with requests.request(method, url, ...) which re-resolves the SAME hostname independently. A hostname whose DNS flips between the check and the fetch (classic DNS rebinding, or simple round-robin where only one A record is private) can pass the guard and then connect to an internal/metadata address. The guard correctly blocks redirects (guard_redirects re-validates each hop) and unwraps IPv4-mapped addresses, so this is the remaining gap, and it is exploitable because business domains and contested-source/mention URLs are partly attacker-influenced.

**Fix.** Pin the connection to the IP that was validated: resolve once in netguard, pick a safe IP, and connect to that IP while sending the original Host header (or use a custom requests Transport/HTTPAdapter / a connect-time getaddrinfo hook that re-applies _ip_is_blocked on the actual socket peer). At minimum, re-validate the resolved peer IP at socket-connect time. Keep failing closed on resolution errors as today.

#### [P2 · M] Audit log is incomplete: no source IP/user-agent, logs unauthenticated requests with null actor, no retention/integrity, decodes the token a second time
**Problem.** The _audit_writes middleware (api/main.py) and audit_log table (alembic 0010) record only user_id, method, path, status_code, created_at. There is no client IP, user-agent, request id, or business_id, so a tenant-data-access investigation can't tie an action to an origin or a target tenant. It logs every mutating request including failed/401 ones with user_id=NULL (noise and no attacker IP). It re-decodes the JWT itself (duplicating deps.get_current_user work and trusting the token rather than the resolved user). There is no retention policy, no tamper-evidence, and GET reads of tenant data are never logged at all — so read-side tenant data access is invisible.

**Fix.** Capture request.client.host (respecting a trusted X-Forwarded-For only behind a known proxy), user-agent, a request id, and the path's business_id. Skip or separately bucket 401/403s. Reuse the already-resolved user from request.state instead of re-decoding. Add a retention/rotation policy and consider append-only/hash-chained storage for the audit table. Add read-side audit logging (at least for sensitive GETs that expose another tenant's data) to support breach forensics.

#### [P2 · S] No HTTP security headers and overly-broad CORS on the API
**Problem.** api/main.py adds only CORSMiddleware (allow_credentials=True with allow_methods=["*"] and allow_headers=["*"]) and no security-header middleware. There is no HSTS, X-Content-Type-Options, X-Frame-Options/frame-ancestors, Referrer-Policy, or Cache-Control: no-store on authenticated JSON responses. Combined with the missing Secure cookie flag, the lack of HSTS means a downgrade-to-HTTP can leak the session cookie; the absence of no-store risks sensitive tenant JSON being cached by intermediaries. allow_headers=["*"] with credentials is broader than needed.

**Fix.** Add a middleware that sets HSTS (in prod), X-Content-Type-Options: nosniff, X-Frame-Options: DENY (or CSP frame-ancestors 'none'), Referrer-Policy: no-referrer, and Cache-Control: no-store on authenticated responses. Tighten CORS allow_headers to the explicit set actually used (Content-Type, X-CSRF-Token, Authorization). Ensure the Next.js console also ships a CSP. These pair with the Secure-cookie fix.

#### [P2 · S] Inline job mode runs paid LLM/crawl work inside the web request process
**Problem.** With JOB_WORKER=inline (the default in settings.py, and the documented local mode), trigger_job (jobs_router.py) schedules _jobs.run_job via FastAPI BackgroundTasks, so audit/cycle/normalize jobs execute in the web process. #### [P0 · L] Headline metrics rest on a 44-case golden set dominated by 2 businesses and one labeler -- not trustworthy enough to sell nationally
**Problem.** eval_data/golden.jsonl has 44 cases but 42 are just two businesses (Team Unstoppable 23, Northwestern Mutual 19); only 2 cases are a third business and there are only 4 'positive' labels vs 17 mixed / 15 neutral / 8 negative. #### [P1 · M] Client-facing metrics carry no confidence interval / sample size and pool unequal engine coverage -- the deliverable over-states certainty
**Problem.** diff(), _run_series, and the report's 'Metrics This Period' table present AVG(goal_alignment), contested_rate, owned_rate as point numbers (e.g. 'Goal alignment 0.42 -> 0.55, improving') with only a 0.02 'NOTABLE' floor (report_generator.py:472) as a guard. #### [P1 · M] Scoring judge is a single cheap-tier LLM with prose-only calibration and no abstention/uncertainty -- the core metric is a black box prone to drift
**Problem.** score_answer routes the high-volume scoring pass to the CHEAP tier (Haiku, ai_state_audit.py:683) -- the single most accuracy-sensitive call uses the weakest model, justified purely as 'the biggest cost lever'. Calibration lives entirely as English prose in SCORING_SYSTEM (lines 638-667) with hand-tuned bands and 'commonly scored too harshly' caveats -- brittle, hard to audit, and exactly what silently shifts on a model swap. There is no self-consistency / multi-judge check, no calibrated confidence per score, and no abstain path: every answer gets a hard sentiment+number even when the model is unsure. The MEMORY note that the judge over-penalizes goal_alignment confirms residual bias. For a product whose entire output is these two numbers, single-cheap-judge is thin.

**Fix.** Validate that the cheap tier actually matches the full tier on the (expanded) golden set per stratum; if it underperforms, score on the mid tier or use cheap-with-full-tier spot checks. Add an uncertainty signal (self-consistency across 2-3 samples, or have the judge emit a confidence) and route low-confidence answers to human review instead of forcing a number. Consider an ensemble / second-judge on a different provider for contested (scam/fraud) cases where errors are most damaging. Keep the calibration in the prompt but back it with the held-out eval so drift is caught.

#### [P1 · L] Content generator's only anti-fabrication control is an LLM self-rubric + regex -- no external fact/claim/citation verification before a human sees a 'compliant' draft
**Problem.** content_generator.py generates drafts, then 'checks' them with _evaluate (a CHEAP-tier LLM grading itself; EVAL_SYSTEM caps score at 0.4 for fabrication) and _compliance (cheap LLM + a 4-rule regex in _COMPLIANCE_RULES). For a reputation product whose drafts assert facts about a real business (credentials, awards, 'licensed', 'board-certified', review counts), an LLM grading its own output is a weak fabrication control -- the same model family that hallucinated a credential will often rate it 'accurate'. **Fix.** Add a grounded fact-check step: maintain a per-business verified-facts store (from the crawl + onboarding) and require any specific factual claim to be either traceable to that store or converted to an [INSERT] placeholder -- enforced, not suggested. Flag drafts containing unverifiable specific claims (numbers, credentials, superlatives, named awards) for mandatory human verification regardless of rubric score. Strengthen the deterministic compliance rules and keep the LLM screen as a second layer, not the primary. Log every claim->source mapping so the reviewer reviews evidence, not just prose.

**Problem.** timeline_estimator.py uses BASE_MONTHLY_GAIN=0.12 goal_alignment/month, DOMINANCE_TARGET=0.6, entrench_drag=1-0.6*grade, and fixed optimistic/conservative multipliers (0.65x/1.75x) -- all invented constants ('literature-based', no citation). acceleration_advisor.py LEVERS assign specific monthly-gain weights per guest article (0.005), link (0.004), video (0.0035), etc., admitted to be 'deliberately conservative ... Make the feedback_loop's learned priors POOL across businesses (a global prior) so a new client benefits from the cohort, not just its own sparse history. Keep ranges wide and confidence-gated, and never let a single-engine/ungrounded audit feed a timeline.

#### [P1 · M] Competitor 'appearance rate' and citation classification use crude substring/token heuristics that will mislabel real businesses

#### [P2 · M] Persona/location 'lenses' are a relabeling of the same generic engine call, not a real audience simulation -- yet presented as 'what different audiences see'

### Multi-tenancy, accounts, admin & customer onboarding (11)

#### [P0 · XL] No organization/agency layer: tenancy is a flat user->business map with no account boundary
**Problem.** The entire tenancy model is three tables (alembic 0007_auth.py): `users` (role admin|client), `business_access` (user_id->business_id, viewer|editor), and `businesses`. There is no `organizations`/`accounts`/`agency` entity anywhere in the schema or code (grep for organization|org_id|agency|tenant_id|account_id finds zero matches in app code). This means: (1) a real SaaS customer 'account' does not exist as a first-class object -- you cannot represent 'Acme Marketing Agency manages 40 client businesses' or 'one company with a marketing team of 5 users sharing 3 brands'; access is granted business-by-business, user-by-user by a global admin. (2) Billing, plan/quota, suspension, and contract all have nothing to attach to -- the unit a national SaaS sells to (an org with N seats and N businesses) is unmodeled. (3) There is no way to scope an 'account admin' (a customer's own admin who manages their own users/businesses) -- the only admin is YOUR global super-admin who sees every tenant's data (auth.py accessible_business_ids returns None=ALL for role=='admin'). Every customer-side org-management action must currently be done by your staff.

**Fix.** Introduce an `organizations` table (id, name, plan, status, created_at) and make it the tenancy root. Add `org_id` to `users` and `businesses` (every business belongs to exactly one org; every non-super-admin user belongs to exactly one org). Split the role axis into two: a platform role (super_admin/support for YOUR team) vs an org role (org_owner/org_admin/member). `business_access` stays for fine-grained per-business viewer/editor, but membership and 'see all businesses in my org' is derived from org_id. Backfill: wrap existing businesses/users into a default org in the migration. This is the foundational change; most findings below depend on it.

#### [P0 · XL] No customer self-serve onboarding: signup, email verification, password reset, and invites are entirely absent
**Problem.** There is exactly one auth surface: POST /auth/login, /auth/logout, /auth/me (auth_router.py) and admin-only POST /admin/users (admin.py). The console has a single login page and no signup/forgot-password/invite-accept route (only src/app/login/page.tsx exists; grep for signup|register|password.?reset|forgot|verify.?email|invite across app source finds nothing). Users are created only by your global admin typing an email+password into admin/users/page.tsx; the new user's password is set BY the admin and there is no mechanism to deliver it, no email is sent (there is no email/SMTP integration anywhere in the codebase), no email-verification step, and no self-service password reset or password-change endpoint (auth.py never UPDATEs password_hash after creation). For a product sold nationally this means every single account, every team member, and every password reset is a manual ops ticket for your team -- onboarding cannot scale past a handful of hand-held customers.

**Fix.** Build the standard self-serve account lifecycle: (1) transactional email provider integration (SES/SendGrid/Postmark). (2) Signup -> creates an org + org_owner user in 'pending' state, sends a verification email with a signed token; account inactive until verified. (3) Invite flow: org_owner/admin invites teammates by email (an `invitations` table with token, role, expiry); invitee sets their own password on accept -- replaces the admin-types-your-password antipattern. (4) Forgot-password + reset (single-use, expiring, hashed token table) and an authenticated change-password endpoint. (5) Rate-limit and audit all of these. Add the corresponding console pages (/signup, /forgot, /reset, /accept-invite).

#### [P0 · L] No per-tenant LLM key / provider isolation: all tenants share one process-wide Anthropic key
**Problem.** Engine API keys are read from process env once at import time and shared by every tenant: ai_state_audit.py reads ANTHROPIC_API_KEY/OPENAI_API_KEY/etc. as module globals (lines 70-76), and config.py exposes them as static fields (lines 29-32). No key is keyed by business_id or org_id anywhere. Consequences for a national multi-tenant SaaS: (1) You cannot attribute true provider cost or enforce provider rate limits per tenant -- one heavy tenant's audits consume the shared key's rate limit and starve everyone. (2) You cannot offer 'bring your own key' (which many agency/enterprise buyers expect for data-handling and cost reasons). (3) A single leaked/rotated key is an all-tenant outage. (4) There is no per-tenant kill switch at the key level. This is acceptable for the current single-key dev reality noted in the brief, but it blocks selling to many tenants at once.

**Fix.** Move provider credentials out of module-global env into a per-tenant (org-level) secrets store: an encrypted `org_credentials` table (envelope-encrypted with a KMS/Fernet key, never returned to the client) plus a resolution layer so audit/agent calls fetch the calling org's key, falling back to a platform pooled key for tenants on your managed plan. Refactor ai_state_audit.py and config.py to take keys as parameters resolved per request rather than import-time globals. Add per-tenant provider rate-limit accounting.

#### [P0 · L] No account lifecycle: cannot suspend, deactivate, offboard, or delete a user or tenant; no data export
**Problem.** The `users.is_active` flag exists (0007_auth.py) and is enforced on login/each request (auth.py:90, deps.py:42), but NOTHING ever sets it to false -- there is no deactivate/suspend endpoint (grep confirms UPDATE users only sets last_login_at; no DELETE FROM users route; admin.py has create + grant/revoke access only). Gate destructive actions behind confirmation + audit_log.

#### [P1 · M] No self-serve provisioning of a new business: budget, monitor keywords, and competitors cannot be set via the API/console

#### [P1 · L] Role granularity is too coarse for a multi-customer org and conflates your-team admin with customer admin
**Problem.** There are only two user roles (admin|client) and two access roles (viewer|editor) (0007_auth.py). 'admin' means GLOBAL platform super-admin who sees and can edit EVERY tenant's businesses (deps.require_admin -> auth.can_edit_business returns True for any business; accessible_business_ids returns None=ALL). #### [P1 · L] No operator/support console for YOUR team: you run support by becoming a god-mode tenant admin in the same app

#### [P1 · L] No usage metering, quotas, or plan/entitlement enforcement tied to the account
**Problem.** The only spend control is the per-business monthly_budget_usd cost gate in the engine (fail-closed, good) -- but it is per-business dollar budget, not a plan/entitlement system, and (per finding #5) it can't even be set without SQL. **Fix.** Once orgs exist (finding #1), add a `plans`/entitlements layer: seat count, max businesses, monthly audit/LLM-spend allowance, feature flags per tier. #### [P2 · L] No SSO/SAML/SCIM for enterprise and agency buyers
**Problem.** Auth is local email+password JWT only (auth.py, auth_router.py); there is no OIDC/SAML SSO and no SCIM provisioning (grep for sso|saml|oauth finds nothing in app code). Mid-market and enterprise US buyers -- exactly the agencies and multi-location businesses this product targets -- frequently require SSO (Okta/Azure AD/Google Workspace) as a procurement gate, and larger accounts expect SCIM for automated user provisioning/deprovisioning. Absence of SSO will lose or stall enterprise deals and forces manual user lifecycle.

**Fix.** Add OIDC/SAML SSO at the org level (org configures its IdP; users in that org's verified domains log in via SSO), behind a higher plan tier. Add SCIM later for automated provisioning/deprovisioning. The org_id model from finding #1 is the prerequisite (SSO config and domain claims attach to the org).

#### [P2 · M] JWTs are stateless with a 12-hour TTL and no revocation: deactivation/offboarding isn't immediate
**Problem.** Tokens are stateless HS256 JWTs with default TTL 720 minutes / 12 hours (settings.py jwt_ttl_min default '720'), and there is no token revocation/denylist or token-version/session table. get_current_user does re-check users.is_active on every request (deps.py:42), which partially mitigates this for user deactivation -- but there is no jti/session-version, so you cannot revoke a specific stolen token, force-logout a user, or invalidate sessions on password reset, and any future code path that trusts the token claims without the is_active DB check would keep honoring a 12h-valid token for an offboarded user. logout only clears the cookie client-side; the JWT remains valid until expiry.

**Fix.** Add a session/token-version mechanism: store a token_version (or last_password_change) on the user and embed+verify it in the JWT, bumping it on password reset, deactivate, and force-logout so existing tokens are invalidated immediately. Optionally a short-lived access token + refresh token with a server-side refresh-session table for true revocation. Tighten the default access-token TTL.

#### [P2 · S] Email is treated as an unvalidated free-text string; no format/normalization/uniqueness-of-real-identity guarantees
**Problem.** LoginRequest and CreateUserRequest type email as a plain `str` (schemas.py:12,32) with no validation -- not pydantic EmailStr -- so malformed or whitespace-laden emails are accepted at creation. Case-insensitive uniqueness is enforced by a functional index (0007_auth.py idx_users_email_lower) which is good, but combined with the absence of email verification (finding #2) there is no proof the address is real or owned by the registrant. For a SaaS where the email is the login identity, the invite/reset target, and effectively the account key, this allows typo'd unrecoverable accounts and impersonation at signup.

**Fix.** Use pydantic EmailStr for all email inputs, normalize (trim + lowercase) before insert/compare, and pair with the email-verification flow from finding #2 so the address is proven owned before the account is active. Reject role-account/disposable domains per policy if desired.

#### [P0 · L] No entitlement gate on the work-triggering chokepoints

There is no deterministic control preventing the engine from being steered toward suppression tactics (e.g. mass-flagging/reporting legitimate negative content, generating defamatory rebuttals, or impersonation), and the only non-injectable deterministic screen (_deterministic_compliance) covers financial superlatives, not ethics/defamation/harassment. For a product whose core risk is reputation-manipulation abuse, the ethical posture needs hard guardrails plus contractual teeth to be defensible to regulators, the press, and enterprise buyers.

**Fix.** Convert the ethics stance into enforced controls: (1) deterministic blocklist screens for suppression/defamation/impersonation/harassment patterns in generated replies and content (alongside the financial rules); (2) an explicit prohibition in the AUP on using the platform to suppress truthful content, mass-report, impersonate, or astroturf, with audit + termination rights; (3) log every human approval decision (you have audit_log — extend it to content/incident approvals) so the human-in-the-loop is provable; (4) publish a short public ethics/responsible-use statement. This makes the 'we crowd out, we don't suppress' claim verifiable rather than aspirational.

#### [P2 · M] Outbound review-request and outreach messaging lacks CAN-SPAM / TCPA / 10DLC controls
**Problem.** The engine drafts SMS + email review-request copy and press-outreach pitches (content_generator.py review_request spec line 144; strategy_generator press_outreach). Today these are drafts a human sends (no auto-send transport is wired), which limits immediate exposure. But the product is positioned to scale outreach, and the moment a send integration is added, US law applies: CAN-SPAM (commercial email must have a physical postal address, a working unsubscribe, no deceptive subject lines) and TCPA + carrier 10DLC rules (SMS to consumers needs prior express consent, opt-out handling, and registered campaigns). The drafted copy specs do not include unsubscribe/opt-out scaffolding or a sender postal address, so if a customer wires up sending they will be non-compliant by default.

**Fix.** Before enabling any send capability, build CAN-SPAM/TCPA controls: require a configured sender postal address and one-click unsubscribe footer injected into all email drafts; require documented opt-in + STOP/HELP handling and 10DLC campaign registration for SMS; suppression-list enforcement. Until then, label drafted SMS/email copy in the UI as 'human-send only — ensure consent and unsubscribe before sending,' and cover sending obligations in the AUP (customer is the sender and responsible for consent).

#### [P2 · M] Financial-services compliance gate is hard-coded and not configurable per regulated vertical
**Problem.** The compliance gate (content_generator.py COMPLIANCE_SYSTEM + _COMPLIANCE_RULES) is specifically tuned to financial-services/broker-dealer marketing (the original client vertical). For a national sale across verticals, regulated customers in healthcare (HIPAA marketing, FDA/health claims), legal services (bar advertising rules), and others get no relevant screening, while non-financial customers get irrelevant flags. There is no way to select a compliance ruleset per business, and no record that a human compliance reviewer signed off (needed for FINRA/SEC-regulated clients who must retain advertising review records under FINRA Rule 2210).

**Fix.** Make the compliance gate pluggable per vertical/business (financial, health, legal, general) with vertical-specific deterministic rules + LLM screen prompts. For regulated verticals, capture and retain the reviewer identity + timestamp + decision on each draft (extends the human-approval audit trail) to support FINRA/SEC advertising recordkeeping. Document which verticals are 'supported with compliance screening' vs. 'general' so sales does not over-promise.

### Observability, deployment, ops & reliability-at-scale (13)

#### [P0 · M] No error tracking / exception monitoring (no Sentry equivalent)
**Problem.** There is zero error-tracking integration anywhere in the codebase (confirmed: no sentry/otel/datadog/rollbar in requirements.txt, requirements-dev.txt, or the Next.js package.json). The system swallows exceptions broadly and silently: api/jobs.py run_job() catches every job failure with `except Exception` and only writes `log.warning` + an `error` column; api/main.py _auto_migrate() and _audit_writes() swallow failures to a warning; cost.py swallows ledger write failures; the LLM orchestrator and agent layers fence/catch heavily. In production these become invisible failures stuck in DB columns and log lines no one is watching. A paying customer's audit can fail and no operator is alerted. You cannot run a national service blind to its own exceptions.

**Fix.** Add Sentry (sentry-sdk with FastAPI + logging integrations) to the API and the worker, and @sentry/nextjs to the console. Capture: unhandled exceptions, every `except Exception` swallow in jobs.run_job/_auto_migrate/cost.record/audit middleware (call sentry_sdk.capture_exception before logging), and LLM-orchestrator failures. Tag events with business_id, run_id, job_id, job_type so failures are attributable per-tenant. Set environment + release tags for deploy correlation. Wire a DSN env var; no-op cleanly when unset (dev).

#### [P0 · M] Structured logging exists but is not wired in — logs are not shippable
**Problem.** logging_setup.py implements JSON-lines logging (REP_LOG_JSON=1), run-scoped context binding, and a single-handler config — but it is effectively dead code. Only runstate.py imports it. The API entrypoint (api/main.py) never calls logging_setup.configure(); it uses a bare logging.getLogger. Worse, ~15 engine modules (ai_state_audit.py:61, orchestrator.py:48, site_crawl.py:113, tracking.py:46, content_generator.py:51, worker.py:36, etc.) each call `logging.basicConfig(...)` with a human format at import time — the FIRST import wins and locks the root handler to plain text, so REP_LOG_JSON never takes effect and structured/JSON logs are never produced in the real process. There is no request_id, no per-request correlation in the API, and no log aggregation target. Operating multi-tenant at national scale requires queryable, correlated logs.

**Fix.** Call logging_setup.configure() once at API startup (lifespan) and at worker startup; delete the scattered logging.basicConfig() calls from every engine module (replace with logging_setup.get_logger). Add an API middleware that generates a request_id (and binds business_id/user_id) into the log context so every line for a request is correlatable. Default REP_LOG_JSON=1 in the container so stdout is JSON. Ship container stdout to a log aggregator (e.g. Grafana Loki, Datadog, or CloudWatch) — document the target in DEPLOY.md.

#### [P0 · L] No metrics, dashboards, or alerting — operating blind
**Problem.** No metrics instrumentation exists (no prometheus-client/OpenTelemetry/statsd anywhere). There is no way to see request rate/latency/error rate, job queue depth, job success/failure rate, LLM call volume/latency/spend per tenant, budget-cap hits, or DB pool saturation. The connection pool (api/pool.py) is hardcoded max_size=8 with no visibility into exhaustion. cost.py tracks spend per business in a table but nothing exposes it as an operational metric or alerts when a tenant nears its cap or when _unrecorded_writes>0 (which silently fails budget checks closed). With no metrics there is no alerting and no on-call signal: outages and runaway cost will be discovered by customer complaints.

**Fix.** Instrument the API with prometheus-client (or OTel metrics) exposing /metrics: http_requests_total/latency by route+status, db_pool_in_use, llm_calls_total + tokens + est_cost by provider/operation, jobs_in_flight, job_failures_total. Emit a queue-depth gauge from the worker. Stand up Prometheus + Grafana (or a hosted equivalent) with dashboards for the golden signals + LLM spend. Define alert rules (error-rate spike, queue backlog, job failure rate, budget cap breaches, pool exhaustion, worker heartbeat missing) routed to an on-call channel (PagerDuty/Opsgenie/Slack).

#### [P0 · M] Health endpoint is shallow — no readiness/liveness separation, no dependency checks
**Problem.** api/main.py exposes only GET /health returning a static {"status":"ok"} — it never checks the DB, the connection pool, or migration state. A container can report healthy while Postgres is down or migrations failed (note _auto_migrate swallows failures to a warning and continues serving against an un-migrated DB). There is no liveness vs readiness distinction, so an orchestrator (k8s/ECS/Render) cannot gate traffic on real readiness or restart a wedged process. The worker process has no health/heartbeat endpoint at all, so a dead worker (see worker-crash finding) is undetectable.

**Fix.** Add /livez (process up) and /readyz (SELECT 1 via the pool + migration head check + verify a required engine key is present). Make /readyz fail when the DB is unreachable so the load balancer drains the instance. Have the worker write a heartbeat (timestamp row or push to a metrics gauge) and add a check that alerts if no worker heartbeat in N seconds. Wire these into the deploy platform's health checks and add a HEALTHCHECK to the Dockerfile.

#### [P0 · L] Background-job system has no retries, dead-letter, timeouts, or stuck-job detection
**Problem.** The job table (alembic 0008_api_jobs.py) has only status/error/timestamps — no attempts/max_attempts, no next_run_at, no lease/locked_until, no dead-letter. jobs.run_job() runs a job exactly once; on failure it marks 'failed' with no retry. Critically, if the worker process dies mid-job (crash, OOM, deploy/restart) the row is left status='running' forever — there is no stuck-job reaper, and enqueue() refuses to queue a new job of the same type while one is 'queued' or 'running' (jobs.py:84-90), so a single orphaned 'running' row permanently blocks all future audits/cycles for that business with no recovery path. In inline dev mode, jobs run via FastAPI BackgroundTasks (jobs_router.py:42) which are lost entirely if the web process restarts before the task runs. There is no operator view of failed jobs across tenants.

**Fix.** Add attempts/max_attempts, locked_by/locked_until (lease), and next_run_at columns; reclaim leases whose locked_until has expired (this both retries crash-orphaned jobs and unblocks the same-type guard). Implement bounded retries with backoff for transient failures and a terminal dead-letter status for poison jobs. Add per-job-type timeouts. Add a reaper that requeues 'running' jobs older than a threshold and alerts. Build an admin endpoint + console view listing failed/stuck jobs across all businesses with retry/cancel actions. Strongly prefer a battle-tested queue (e.g. a Postgres-backed RQ/Dramatiq/SAQ, or Celery) over the bespoke poller for national scale.

#### [P0 · M] Worker loop crashes on any DB blip with no supervision or graceful shutdown
**Problem.** api/worker.py run_forever() calls _next_queued() which opens a fresh db() connection every poll with no try/except. A transient DB error (Postgres failover, restart, network blip, max_connections) raises out of the loop and kills the worker process. Nothing supervises or restarts it — docker-compose has no restart: policy, and there is no systemd/k8s manifest. The final status UPDATE in run_job() (jobs.py:118-123) is also unguarded: if the DB is unavailable when a job finishes, the worker crashes and the job is stranded in 'running'. There is no SIGTERM handling, so a deploy/scale-down kills the worker mid-job rather than draining. A single worker with no HA also means zero job throughput during any restart.

**Fix.** Wrap the poll loop in try/except with backoff so transient DB errors are logged + retried, not fatal. Add SIGTERM/SIGINT handlers for graceful drain (finish/requeue the in-flight job, then exit). Set restart: unless-stopped in compose and a real supervisor (k8s Deployment / ECS service / systemd) in prod. Run >=2 worker replicas (the atomic claim already makes this safe). Combine with the lease/reaper above so a killed worker's job is reclaimed.

#### [P0 · XL] No hosted production deployment story — docker-compose only, dev-grade config
**Problem.** The only deployment artifact is docker-compose.yml (local) and DEPLOY.md, which itself labels the prod section 'Phase 5 readiness; ratchet before public exposure' with hardening 'remaining'. There is no managed-Postgres provisioning, no secrets manager, no IaC, no zero-downtime path. Concrete prod-readiness gaps in the artifacts: (1) the API container runs `uvicorn ... ` single-process with no Gunicorn/multi-worker and the convenience main() even sets reload=True; (2) Dockerfile runs as root with no non-root USER and no HEALTHCHECK; (3) docker-compose has hardcoded postgres/postgres credentials and no restart policies; (4) migrations run via _auto_migrate() inside every API process at startup — with multiple replicas this races and, on a backward-incompatible migration, breaks zero-downtime deploys. The Next.js console has no Dockerfile and only a Vercel hand-wave.

**Fix.** Stand up a real hosted environment: managed Postgres (RDS/Cloud SQL/Neon) with enforced TLS, a secrets manager (AWS Secrets Manager / Doppler / SSM) for JWT_SECRET + API keys + DB creds (never env literals in compose), and IaC (Terraform) for reproducibility. Run the API under Gunicorn+uvicorn workers (or multiple uvicorn workers) behind a load balancer; add a non-root USER and HEALTHCHECK to the Dockerfile; pin restart policies. Decouple migrations from app startup into a dedicated release/migrate step (run-once job) so replicas don't race and deploys are zero-downtime; adopt expand/contract migration discipline. Provide a console deploy target (Vercel project or a Node Dockerfile) with NEXT_PUBLIC_API_BASE_URL wired.

#### [P0 · M] No database backups, PITR, or disaster recovery
**Problem.** There is no backup/restore/PITR/DR provision anywhere — the only `backup` reference in the repo is absent from code/infra, and docker-compose persists data to a local `pgdata` volume with no backup. This database is the entire product's state: tenants, audits, answers, content drafts, cost ledger, audit_log (the compliance/attribution record), and the durable LangGraph human-gate checkpoints. Losing it loses every customer's reputation history and any in-flight human-gated agent review, with no recovery. No documented RPO/RTO. This is unacceptable for a paid national service and likely fails customer security reviews / data-processing commitments.

**Fix.** Use a managed Postgres with automated daily backups + point-in-time recovery (WAL) enabled, define and document RPO/RTO targets, and actually test a restore on a schedule (an untested backup is not a backup). Add logical dumps to object storage as a second line of defense, with retention. Document the DR runbook (restore steps, failover region option). Treat the LangGraph checkpoint tables and audit_log as backup-critical.

#### [P1 · L] CI/CD is immature — no staging env, no deploy automation, no rollback, weak quality gates
**Problem.** CI (.github/workflows/ci.yml) runs tests + a blocking F/E9 ruff subset, but the full ruff ruleset, bandit SAST, mypy, and gitleaks are all `|| true` / continue-on-error (advisory), so real lint, type, and secret-scan regressions cannot fail the build. Coverage floor is 50% (baseline measured 57.5%). There is NO continuous deployment workflow at all — no build-and-push image, no staging environment, no automated deploy, no migration-on-deploy step, and therefore no defined rollback procedure. The eval gate is weekly and self-skips when ANTHROPIC_API_KEY is absent, so scoring-quality regressions can ship and sit undetected for up to a week. For a national service you need a tested path from merge to production and back.

**Fix.** Add a CD pipeline: build/push the API+worker image (tagged by SHA), deploy to a persistent STAGING environment automatically on merge, run smoke/health checks, then gate prod promotion (manual approval or auto). Make image rollback trivial (deploy previous tag) and document it. Ratchet the advisory gates to blocking (bandit medium+, gitleaks, mypy clean on touched modules) and raise the coverage floor. Run the eval gate (or a cheap subset) as a release gate, not only weekly, so scoring drift can't reach prod silently.

#### [P1 · M] No SLOs/SLIs, status page, or capacity model
**Problem.** There are no defined SLIs/SLOs (availability, API latency, audit/job completion time, scoring-judge accuracy floor as a product SLI) and no error budget — ROADMAP grep shows none. There is no public/customer status page to communicate incidents and degradations, which national B2B buyers expect. There is also no capacity/scaling model: pool.py max_size is a hardcoded 8 and the comment notes the engine's per-call db(), the read pool, and the LangGraph PostgresSaver pool all compete for connections under a single Postgres max_connections — with no documented sizing as tenant count grows, connection exhaustion is a latent outage.

**Fix.** Define SLOs (e.g. API 99.9% availability, p95 read latency, audit job completion within X, scoring-judge agreement >= the eval floor as a product SLI) with error budgets, and instrument the SLIs (ties to the metrics finding). Stand up a status page (Statuspage/Instatus/BetterStack) with automated uptime checks. Produce a capacity model: connection budget across pool + engine + checkpointer vs Postgres max_connections, and a documented scaling plan (replica counts, pool sizes, when to add read replicas / a pgbouncer).

#### [P1 · M] No runbooks, incident-response process, or on-call
**Problem.** preflight.py is a one-time first-run go/no-go CLI, not operational runbooks. There is no documented incident-response process, no on-call rotation, no escalation policy, and no runbooks for the failure modes this system actually has: stuck/orphaned jobs blocking a tenant (see job finding), budget fail-closed locking out a tenant's audits (cost.over_budget returns True on any ledger error or unrecorded write), a wedged worker, a missing/expired LLM provider key (preflight flags it but nothing watches it at runtime), DB failover, and migration failures. When a paying customer is broken at 2am, operators have nothing to follow.

**Fix.** Write runbooks for each known failure mode (orphaned 'running' job recovery, worker dead/restart, budget-lockout diagnosis + override, provider-key rotation/outage, DB failover + restore, failed migration rollback) and store them with the repo. Establish an on-call rotation + escalation policy and connect alerting (from the metrics/error-tracking findings) to it. Adopt a lightweight incident process (severity levels, comms via the status page, post-incident review).

#### [P1 · M] Multi-process deployment gaps: in-memory rate limit and no shared coordination
**Problem.** api/ratelimit.py is explicitly process-local (in-memory _ATTEMPTS dict) and its own docstring says 'for multi-process use a shared store later.' DEPLOY.md lists this as hardening still remaining. Under the required multi-replica prod deployment, the login brute-force limiter is trivially defeated by spreading attempts across replicas, and the limit also resets on every deploy/restart. More broadly there is no shared coordination layer (no Redis) for rate limiting, distributed locks, or caching as the service scales.

**Fix.** Move the login rate limiter to a shared store (Redis) keyed per-IP/email so the limit holds across replicas and survives restarts; add lockout/backoff on repeated failures. Provision a managed Redis as part of the prod stack — it also gives you a home for distributed locks and a faster job queue if you adopt RQ/Dramatiq. Until shared, document that the API must run single-replica (which conflicts with the scaling requirement), making this a launch blocker for scale.

#### [P2 · M] No customer support / operations tooling for tenant-level issues
**Problem.** Operational tooling for support is thin. The admin surface (routers/admin.py) manages users/access/businesses, and jobs_router exposes per-business job lists, but there is no cross-tenant operations console: no global failed-jobs view, no per-tenant spend/budget dashboard for support to diagnose a 'why did my audit stop' ticket (budget fail-closed is invisible to the customer), no way to inspect a tenant's recent errors, replay a failed job, or impersonate/read-only-view a tenant's state for support. audit_log exists but has no UI. Without this, every support request becomes a DB query by an engineer.

**Fix.** Build an internal ops/support view (admin-gated): cross-tenant job/failure browser with retry/cancel, per-tenant cost-vs-budget and budget-override control, recent-errors-per-tenant (fed by the error tracker), and an audit_log viewer. Add a safe read-only tenant-view for support. This sharply reduces engineer toil and time-to-resolution as the customer base grows.
